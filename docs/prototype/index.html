Build notes

Everything this prototype does, and how to build it for real. Written to be read cold: if you have never seen this project, start at the top and you will have enough.

What this is. A design prototype of scribe-lm, the frontend of Scribe. It is scripted: no model, no network, no library behind it. It is the reference for look, motion and behaviour — not for code. Do not port its DOM or its JavaScript. Read it, then build the app properly.

This tab is scaffolding and does not ship. The two tabs beside it, Ask and Add a book, are the app.

1. The product, cold

Scribe answers questions about philosophy from a library of scanned PDFs, and every claim it makes about a text links to the page it came from. Its backend is alexandria — Hono on Cloudflare Workers, one D1, one R2, everything under /api/. scribe-lm holds no data of its own; it reads that API like any other client.

The thing that makes it worth building: after the model answers, the server looks for every quote on the page the model named, and reports whether it was actually there. Most of this interface exists to show that result honestly.

Vocabulary you need

Work A book, lecture, article or film. What a citation is ultimately about.
Document One concrete file of a Work — a particular PDF, edition or translation. Pagination belongs to the Document, not the Work: page 47 means nothing until you know which edition.
Page One page of one Document, as extracted text. Numbered by position in the PDF; the number printed on the paper is derived from the page offset, so both are shown: p. 9 (PDF p. 21).
Page handle The short name — P1, P7 — a Page is given the first time a tool shows it to the model in this conversation. A model can only cite a handle it was shown, so it cannot cite a page it never read.
Citation A pointer from a claim to a Page, carrying the verbatim words the claim relies on and whether those words were found there.

2. Stack

  • React + TypeScript + Vite. The repo is already scaffolded as a Cloudflare Pages app with one Pages Function proxying /api/* to the worker. Same-origin by construction — never add CORS handling, never add a second API client.
  • Tailwind 4, CSS-first. Every token in this prototype becomes a @theme variable. No arbitrary hex values in components, ever.
  • Vercel AI SDK v7, useChat with DefaultChatTransport. The chat endpoint streams an AI SDK UI message stream, so the hook reads it directly.
  • No component library, no state library. The app is a chat and a drawer. useChat plus two small contexts covers it.

3. Endpoints

GET /api/models — the models whose provider key is set on the worker, and the default.
GET /api/conversations — the callers own conversations, newest first.
POST /api/conversations — { title?, model_id? }.
GET /api/conversations/:id — { conversation, messages }, messages being AI SDK UI messages.
POST /api/conversations/:id/chat — send only the new message; history is loaded server-side.
GET /api/documents/:id and /api/documents/:id/pages — what a citation points at.

4. Feature inventory

Everything in this prototype, in the order you meet it. Each has a matching user story in section 11.

  1. Launch. The wordmark types itself in place at the centre of an empty screen; the model line, composer and suggestions fade up beneath it.
  2. Home. One centred column: wordmark, running <model>, composer, two starting questions. No sidebar, no header chrome beyond the tabs.
  3. Model switcher. Lives in the line under the wordmark, and in the header once a conversation starts. Lists only models with a key set; the rest appear disabled and labelled no key set.
  4. Composer. One instance, which moves from the centre of the home screen to the bottom dock when the conversation starts. Auto-growing textarea, Enter sends, Shift+Enter newlines.
  5. Question. Right-aligned bubble, one corner squared off toward the writer.
  6. Apparatus. While the model searches, a live line names what it is doing by name — searching pages, will to truth. When the answer begins it collapses into one summary line that expands on click.
  7. Answer. Full width, no bubble, revealed a word at a time.
  8. Citations. The quoted words are set one weight heavier, quote marks dropped to faint grey, followed by a status stamp.
  9. Stamps. Filled square: found on the page. Open square: not found, or matched then diverged. Dotted open square: the page has no text layer, so nothing could be checked. Pending: an outline, pulsing.
  10. Margin notes. On a wide screen each citation has a note in the margin, level with the sentence it supports, naming work, creator, printed page, PDF page and verdict. Hovering either end lights both and draws a hairline between them.
  11. Page view. Clicking a citation opens a drawer with the page in its own words and the quote in place. For a partial match it shows where the match stopped. For a page with no text it says so rather than pretending.
  12. Only what is cited. Fades every sentence no citation supports.
  13. Thread rail. Appears only once a conversation exists. Titles arrive a beat late, because the server names a conversation after its first question.
  14. Add a book. Drop zone plus the three steps a file goes through before it is citable.
  15. Keyboard. / focuses the composer, c toggles the dim, Esc closes the drawer and any menu.

Who owns what

  • ModelProvider owns the roster and the selection. RunningModel is one component rendered in two places; do not write a second switcher for the header.
  • Conversation owns nothing but the message list from useChat. A Turn derives everything it renders from one assistant message plus the user message before it.
  • Composer is a single instance whose position is a prop, not a copy. Two textareas means two drafts, and the draft is lost the first time someone sends.
  • PageView is a route-level singleton opened by id, never rendered per citation.

6. Reading a message

An assistant message holds the text of every step, not only the last, and models narrate between tool calls — let me read the fuller context — however firmly the instructions ask them not to. Rendering every text part in sequence shows the reader the model thinking out loud and calls it the answer.

The answer is the text after the final step-start. Everything before it is apparatus. 

const steps  = splitOn(message.parts, 'step-start');
const answer = steps.at(-1).filter(isText);
const work   = steps.slice(0, -1);      // narration + tool calls

The stream ends with a data-citations part: every citation in the answer, its page, and whether the quote was found there. Until it arrives, every citation in the message renders pending. It is never faked, never optimistic, and never inferred on the client.

7. The citation pipeline

  1. Every page a tool shows the model is labelled with a handle, [P7].
  2. The model cites as [P7 "verbatim words"], or as "verbatim words" [P7], which is what smaller models tend to write.
  3. After the answer, the server normalises each quote — case, diacritics, ligatures, punctuation, line-break hyphens — and looks for it on that page, or across the break onto the next.
  4. The result, verified, unverified or unverifiable, is streamed to the reader and saved with the message.

What each status means to a reader

verified The words are on the page. It does not mean they support the claim. Say found on the page, never a bare verified, and never a tick.
not_found Not on that page in any reading of it.
partial_match The quote begins on the page and then diverges: either the scan is damaged mid-quote, or the model misquoted. Show where it stopped; do not assign blame.
quote_too_short Under five words, which matches too much text by accident to count as evidence.
unverifiable The page has no text layer. Nothing could be checked, which is not the same as failing a check.

Mapping a citation to its words

Today the client has to find each citation in the answer text by re-implementing the server regex, and the two have to agree forever, including on curly quotes and quotes containing quotes. Do not scatter that regex. One module, one exported function, one test file of the awkward cases. The proper fix is for the server to send marker offsets, and that ask is written up in plans/scribe-citations-api.md along with three others. Read it before building this part.

8. DRY, and the traps

  • One status map. Colour, stamp shape, verdict wording and tooltip all come from a single CITATION_STATUS record keyed by status and reason. A colour written inline in a component is a bug: the next status will be added in four places and shown in three.
  • One page formatter. describePage() exists on the server and produces Work — Creator — p. 9 (PDF p. 21). Mirror it once on the client and call it everywhere: margin note, page view, tooltip, empty state.
  • One copy file. Every user-facing string — verdicts, empty states, failures — in one module. The honesty of this interface lives in its wording, and wording scattered across components drifts.
  • Tokens, not values. Three status inks and nothing else coloured. If a component needs a new colour, the design is wrong, not the palette.
  • No mobile fork. One component tree, container queries. Never isMobile inside a component, and never a second layout component for small screens.
  • Status never rests on colour alone. Shape and words carry it too. Enforce that in the stamp component, not by convention.
  • The API is additive-only. Two frontends, one publisher. Code written against the payload as it stands keeps working; a breaking change is a planned two-repo event, not a commit.

9. Animation

What Spec
Wordmark typing 86ms per glyph, 190ms over the hyphen. Every glyph is laid out before the animation starts and only its opacity changes, 240ms linear; the caret is absolutely positioned and walks to the trailing edge of each character. Inserting characters one at a time jitters the whole line — do not.
Home fade-up Model line, composer, suggestions: 500ms cubic-bezier(.22,.61,.36,1), staggered 130ms, 4px rise.
Answer reveal Word at a time, 32ms apart, each fading 280ms linear. A citation waits 200ms before the next word, because the eye needs to land on it.
Verification Stamps resolve in document order, ~290ms apart, each with a 3px nudge on its margin note. It should read as a pass down the page, not a flicker.
Tie line 320ms stroke-dashoffset draw. It starts at the columns edge level with the quote, never at the quotes own right edge — a citation ending mid-line would otherwise drag the curve back across the prose.
Page view 380ms slide, same easing. One drawer at a time.
Reduced motion Skip the typing, print the answer whole, resolve every stamp at once, keep the drawer instant. Honour it with a real branch in the code, not only a CSS override — a 40-second word-by-word reveal is still a 40-second wait.

10. Responsive and accessible

  • Container queries on the app shell, not viewport media queries. At 1040px the margin column folds into footnotes under the answer. At 560px the rail goes, the header compresses, and the page view takes the full width.
  • Every interactive element reachable by keyboard with a visible focus ring. Citations are focusable and open their page on Enter.
  • Stamps carry an accessible label with the verdict and the page, since the square itself says nothing to a screen reader.
  • The drawer traps focus and returns it to the citation that opened it.
  • --ink-faint is for decoration and placeholders only. Never set a verdict or a control in it.

11. User stories

Acceptance criteria, not aspirations. The build is done when every one of these is true.

Asking

US-1 — I land on the app and know what it is.
The wordmark types itself in place, the composer is focused and ready, and the model in use is named without my having to open anything.
US-2 — I ask a question and see it accepted.
My question appears as a bubble immediately; the composer clears and disables; the home screen gives way to the conversation with the composer docked at the bottom. My draft is never lost in that transition.
US-3 — I can tell the difference between working and hung.
While the model searches, a line names each step as it happens, by name and by book. If nothing has happened for a while I can still see what the last step was.
US-4 — I read the answer, not the narration.
Only the text after the final step boundary is set as the answer. Narration and tool calls collapse into one apparatus line that expands on click.
US-5 — I change models and know what it applies to.
The switcher lists only models with a key set and labels the others. A change applies to the next answer; earlier answers keep, and display, the model that wrote them.

Evidence

US-6 — I can see which words are the evidence.
Quoted words are visibly heavier than the prose around them, with the quote marks receding. I can tell at a glance which part of a sentence the source supplied.
US-7 — I can see whether a quote held up, without clicking.
Each citation carries a stamp whose shape and colour both encode the status, and a margin note that says it in words. Nothing about the status is carried by colour alone.
US-8 — I watch the checking happen.
Citations render pending while the answer streams, and resolve in order once data-citations arrives. At no point does an unchecked citation look like a checked one.
US-9 — I can go to the page and judge for myself.
Clicking a citation or its note opens the page with the quote in place, in the pages own words. A partial match shows where it stopped matching. A page with no text layer says so plainly instead of showing an empty drawer.
US-10 — I can see what the answer is not standing on.
One control fades every sentence no citation supports. It is available on every answer and holds its state across answers in the session.
US-11 — I can trace a citation to its note and back.
Hovering or focusing either end lights both and draws the hairline between them. The hairline never crosses the text of the answer.
US-12 — I am never told a quote is right when only its presence was checked.
No tick, no bare verified, no green reassurance. The wording everywhere is found on the page.

Conversations, and the rest

US-13 — My questions are kept and named.
A conversation appears in the rail as soon as it exists, titled once the server has named it, without the layout jumping when the title lands.
US-14 — I can start a new question without losing the last.
New question returns to the home screen; the previous conversation remains in the rail and reopens with its citations and their statuses intact.
US-15 — I can use this on a phone.
At narrow widths the margin becomes footnotes under the answer, the rail becomes reachable rather than gone for good, the page view is full width, and no horizontal scroll appears at any width.
US-16 — I can drive it from the keyboard.
/ focuses the composer, c toggles the dim, Esc closes the drawer and menus, Tab reaches every control with a visible ring.
US-17 — When it breaks, I am told what broke.
Provider failures are named in the readers terms — out of credit, rate limited, provider down — not as a stack trace and not as a generic apology. A failed answer leaves the question in place and the composer usable.
US-18 — I can add a book.
A dropped PDF is accepted and shown in a queue, and the interface says what will happen to it before it is citable. Until ingestion exists behind it, the interface says that too, rather than implying success.

12. Do not build

  • Client-side verification. The check belongs on the server, after the answer. Never re-check, never retry a failed citation, never soften one.
  • Optimistic citations. Nothing renders as checked before data-citations arrives.
  • A tick, a cross, or a confidence score. None of the three is what was measured.
  • Markdown headings inside answers. The model is instructed to write plain prose. Support paragraphs, emphasis and citations; nothing else.
  • Avatars, three-dot typing indicators, per-message action bars. The apparatus line already says what is happening, by name.
  • Components copied out of stylus, the other frontend. The duplication between the two is deliberate: sharing UI would anchor this app to Vue and to stylus layout assumptions. Share technical code, never business logic.
  • Any database in this repo. alexandria owns every row.
